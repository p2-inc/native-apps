# Security model and deployment responsibilities

[Index](README.md) · [Protocol](protocol-and-flows.md) · [Troubleshooting](development-and-troubleshooting.md)

This document describes implemented mechanisms and their limits, not an audit, security certification or claim of OAuth/FiPA conformance. The demo is development configuration. Android SDK and sample support is planned and unimplemented; no Android attestation or key-storage guarantees exist here.

## Trust boundaries

The native UI and SDK run in the same application process. Passwords, new passwords, OTPs and recovery codes are visible to application code before TLS delivery; moving input out of Keycloak's origin removes the browser's origin/address-bar boundary. A public client ID and `native-auth.enabled=true` allowlist do not establish that a caller is your signed app. Native flows are appropriate only with an explicit trust/deployment policy for the participating application. There is **no** App Attest, Play Integrity or equivalent client/device attestation validation; metadata's attestation block is reserved and false.

The extension endpoint translates native inputs into Keycloak authentication/required-action operations. It reuses credential providers for passwords, TOTP, passkeys and recovery codes, but custom flow orchestration and internal Keycloak APIs are additional trusted server code. Resource servers remain responsible for access-token signature, issuer, audience, expiry, authorization and applicable DPoP validation. SDK JWT decoding is not validation. Native authentication creates server sessions/tokens, not browser SSO cookies.

## Implemented protections

- **PKCE:** SDK creates a fresh S256 verifier/challenge per login/step-up; token exchange proves original verifier. Demo client requires S256. Server enforcement is client-configurable: a non-PKCE client can start unprotected requests, and `plain` is accepted if policy allows. Require S256 administratively. Codes are normal single-use Keycloak codes; failed exchange can consume one.
- **Continuation binding:** [AuthSessionCodec](../keycloak-native-auth/native-auth-core/src/main/java/io/phasetwo/keycloak/nativeauth/core/session/AuthSessionCodec.java) uses Keycloak JWE direct AES-GCM with realm AES key and `kid`. In-flow value identifies client/root/tab, and server checks native marker, action, pending execution/type and timeout. Previous passive keys must remain available if existing sessions should survive rotation. Treat the JWE as sensitive possession state, not a decoded application object.
- **DPoP:** [DPoPProofChecker](../keycloak-native-auth/native-auth-endpoint/src/main/java/io/phasetwo/keycloak/nativeauth/endpoint/DPoPProofChecker.java) uses Keycloak's validator when its DPoP feature is enabled, including method/URI/time/signature/replay checks. Initial proof binds subsequent native sessions, authorization code and post-login session to the same thumbprint. Missing/different proof on a bound continuation fails. No initial proof leaves the session unbound; later proof does not upgrade it. Binding is opportunistic, not globally mandatory. If DPoP feature is disabled, this checker ignores the header. Verify actual metadata algorithms, token type and deployment policy.
- **Credential checks and throttling:** Wrong factor answers use Keycloak failure handling/brute-force protection where implemented; missing input is not generally counted. Phantom password challenges/dummy hashing reduce obvious username existence signals when default username configuration is used. Different credential availability, timing and deployment configuration still preclude a claim of complete enumeration resistance. Phantom countdown is session-local and not a global rate limiter. No general endpoint/IP rate limiter or emitted `slow_down` exists here.
- **Challenge replay/expiry:** WebAuthn assertions consume stored challenge and new challenge sets replace it; registration uses single-use server entries and user-action timeout. Recovery codes are consumed by Keycloak. Email/SMS/verification codes are salted SHA-256 hashes in auth notes with TTL, attempt limit and resend cooldown; these short codes still need access/rate protection. Push uses upstream expiring challenge state, signed device decisions and number match in the demo. JWE rotation alone does not make every continuation one-time; server execution and challenge state govern reuse.
- **Enrollment freshness:** Passkey registration and push enrollment start require a valid user/session and recent user-session authentication, default 300 s. Refreshing tokens does not reset this time. Optional native-client-only restriction defaults false. Both options/finish check freshness; invalid finish consumes a registration ID after structural decoding checks, so obtain new options for retry. Mid-flow enrollment uses the authenticated native session/action instead of a preexisting bearer token.

## Redirects, state and nonce

Native initial authentication does not redirect; default code exchange omits `redirect_uri` by design. Server can enforce sentinel/fixed redirect binding; do not mistake an initial client-supplied `redirect_uri` for that policy. Require S256 regardless of redirect mode. Realm-wide fixed-URI metadata has a [per-client limitation](protocol-and-flows.md#server-configuration).

Browser fallback uses a single-use expiring PAR request, server-generated state, registered callback and original PKCE. Native session is removed; it does not hand completed factors to the browser. [WebFallback](../ios/KeycloakNative/Sources/KeycloakNativeCore/WebFallback/WebFallback.swift) checks callback state when expected, extracts code and exchanges with explicit callback URI. Its callback extraction does not independently validate full host/path/issuer; the application owns callback registration and any custom presenter behavior. Default system browser session may reuse browser SSO cookies (`ephemeralWebSession=false`). SDK logout does not clear those cookies.

`LoginParameters.nonce` is optional and copied to OIDC notes, but the SDK does not automatically generate it, validate an ID token or compare returned nonce. Do not use unverified decoded ID-token claims as authorization. There is no native initial `state` validation mechanism comparable to the browser callback; native session/PKCE/key bindings serve distinct purposes.

## Transport, storage and logging

Use HTTPS for issuer, discovered endpoints, API and SMS webhook. [SDK configuration](../ios/KeycloakNative/Sources/KeycloakNativeCore/KeycloakNative.swift) accepts HTTP URLs; it does not enforce TLS in code, so ATS/deployment policy is essential. Demo `start-dev`, HTTP enabled, hostname strict false and local-networking ATS exception are not deployment hardening. Configure external hostname/trusted proxy headers so proof `htu`, issued token issuer and WebAuthn origins agree; prevent untrusted clients from controlling forwarded host/protocol values. Do not expose demo admin/mailpit/resource ports publicly.

[KeychainStore](../ios/KeycloakNative/Sources/KeycloakNativeCore/Credentials/SecureStore.swift) defaults to `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`; credentials, post-login session, push enrollment and key representation are scoped by issuer/client. This is not biometric access control. Automatic key mode prefers Secure Enclave; fallback software keys are exportable in-process and serialized into the configured secure store. Explicitly require hardware keys if your policy needs that guarantee and handle unavailable hardware. Losing/replacing a DPoP key breaks existing bound tokens and push credentials. User switching needs deliberate cleanup/re-enrollment; storage keys do not include user ID.

Passwords/OTPs remain ordinary Swift strings in UI/model/request memory; there is no guaranteed zeroization. Do not persist them, send them to analytics or crash reports, or log raw requests. [ObservingTransport/Redactor](../ios/KeycloakNative/Sources/KeycloakNativeCore/Transport/FlowObserver.swift) masks known credential/session/token/assertion/enrollment/device fields before observer logging, but field-based masking is not protection for arbitrary future payload fields or application logs. Keycloak debug logs include usernames, user-session/challenge IDs and provider context; hash-prefix use for some session references does not mean all server identifiers are redacted. Diagnostics export should be treated as sensitive.

The Java [TranscriptRecorder](../keycloak-native-auth/demo/src/test/java/io/phasetwo/keycloak/nativeauth/demo/TranscriptRecorder.java) masks selected request form fields, while response JSON and some request headers/bodies retain real-looking tokens/session/assertion material. Checked-in transcripts are isolated test artifacts, not a template for recording production traffic. Never commit live credentials, APNs private keys, notification tokens or unsanitized production transcripts. These docs use placeholders.

## Push approval and local biometrics

Use native DPoP-bound user tokens and the same key for device JWTs. No embedded confidential-client secret should be added to the mobile app. A `DeviceTokenProvider` interface exists, but a secret-based provider is not supplied. Fetch pending context from the authenticated device API before displaying or acting on notifications: [PushNotificationPayload](../ios/KeycloakNative/Sources/KeycloakNativePush/PushModels.swift) decodes token claims without independently verifying the realm signature, and the service helper uses this for display. Notification receipt or decoded claims alone are not authentication proof.

Display the client/request context, expiry and number choices, require deliberate approve/deny, and handle concurrent resolution. Number matching and resend cooldown reduce some push mistakes; they do not eliminate malicious login attempts/push fatigue. The typed SDK/default screens expose number match; server PIN mode needs additional raw-param UI. An APNs token update or simulated token does not establish actual delivery. Real delivery and hardware protection remain device/provisioning verification work.

Passkey platform verification may use Face ID/Touch ID or device authentication; Keycloak authenticates the resulting signed WebAuthn assertion under its policy. Native biometric success by itself is not server authentication. SDK DPoP signing keys also do not require a per-request biometric prompt by default.

## Logout and administrator/application responsibilities

`CredentialsManager.logout()` attempts refresh-token server logout then clears local credentials even if offline; direct revoke/logout APIs do not clear application state. Neither operation universally invalidates already-issued self-contained access tokens at every resource server immediately. Honor expiry and required revocation/session policy server-side. Local clear does not remove server sessions/credentials, browser SSO, DPoP key or push enrollment. Password update does not sign out other sessions. Push `forgetEnrollment` only deletes local enrollment; `lockout` disables the user rather than performing ordinary logout.

Before deployment, administrators must define public-client allowlists, S256, appropriate flow requirements/LoA and credential policies, TLS/proxy origins, callback URIs, email/SMS delivery, brute-force/rate limits, timeout/key rotation strategy, audited provider versions, and recovery paths for unsupported actions. Replace demo known secrets and `otpPolicyCodeReusable=true`; leave TOTP reuse disabled unless deliberately justified. ACR 2 is not guaranteed for every user merely by requesting it: the supplied level-2 subflow also checks whether a factor is configured; APIs must enforce required achieved ACR.

Application developers own trusted UI/navigation, input cleanup, consent/approval UX, concurrency/cancellation, persistence failures, account switching, token refresh/step-up retries and resource validation integration. Verify actual device passkeys, associated domains, key restoration, accessibility and APNs before relying on them. Attestation, mandatory binding, global rate limiting and broader conformance/hardware evidence are unresolved hardening work, not implemented protections.
